# Basic HTTP App versus Zap comparison

Date: 2026-09-06. Native macOS and Linux, exact Zig 0.16.0 ReleaseSafe.
This compares the new framework's public App/Response API with its predecessor
[Zap](https://github.com/zigzap/zap). It is a short loopback experiment alongside
the separate [API correctness receipt](2026-09-06-app-api.md).

## Results

Three paired repetitions per profile on each host; rates are requests/second.
The ratio divides the two medians. Ranges include every completed trial.

| Host | Connections / client threads | App median | Zap median | App / Zap | App range | Zap range |
| --- | --- | ---: | ---: | ---: | ---: | ---: |
| macOS | 32 / 2 | 254,261.14 | 245,053.75 | 1.038× | 251,895–255,807 | 218,680–245,550 |
| Linux | 32 / 2 | 363,594.19 | 205,310.36 | 1.771× | 354,069–375,149 | 194,245–208,805 |
| macOS | 1 / 1 | 33,199.20 | 52,808.77 | 0.629× | 32,975–33,225 | 51,338–53,544 |
| Linux | 1 / 1 | 74,385.99 | 72,575.43 | 1.025× | 68,864–83,801 | 65,801–78,006 |

At 32 connections this experiment observed similar throughput on the Mac and
about 77% higher App throughput on the Linux host. The one-connection baseline
shows lower App throughput on Mac and similar medians on Linux. Three short
trials do not establish statistical significance or identify a bottleneck.

All 12 measured trials per host completed. wrk reported 5,357,554 timed requests
on Mac and 6,606,329 on Linux, with zero socket-error and non-2xx-or-3xx counters
in measurements and warmups. Exact status/header/body checks ran before and
after timing. wrk did not individually validate every timed response body or
require each timed status to be exactly 200. Raw latency output is retained
without endorsing latency percentiles or an SLO.

## Matched workload and remaining differences

Both fixtures serve `GET /plaintext` with status 200, Content-Type `text/plain`,
Content-Length 13 and exactly `Hello, World!`. Preflight also checks separate
404 and 405 paths. Request logging is disabled. Each fixture reserves 128
connections. App uses one inline I/O shard and zero application workers;
Zap uses `threads=1`, `workers=1`, `max_clients=128`. Recorded process snapshots
show one process and one thread for each fixture on both hosts.

App registers a normal route and calls its copying `Response.bytes` helper.
Zap checks method/path and uses `Request.setContentType` / `sendBody`. Response
headers and internal defaults can differ. This is not a low-level-engine versus
App comparison and does not isolate framework overhead.

The client runs on the same host as the server, without CPU affinity pinning.
It uses keep-alive, one outstanding request per connection and no Lua script or
HTTP pipelining. Profiles are c1/t1 then c32/t2. Each trial starts a fresh server,
checks its mode and wire output, warms up for one second, measures for three
seconds, checks output again, and stops the server. Across all six pairs, the
order alternates App/Zap, Zap/App, App/Zap, Zap/App, App/Zap, Zap/App.
Client-reported elapsed times, raw counts and actual commands remain in the
trial receipts. The unpinned shared-host client can limit observed throughput.

Every fixture build, warmup and timed trial used **ReleaseSafe**, guarded in the
fixture build and checked in each server's READY output before load. Zig safety
assertions stayed enabled. Zap's inherited facil.io C flags include `-Os`,
`-Wno-return-type-c-linkage`, `-fno-sanitize=undefined` and
`-DFIO_HTTP_EXACT_LOGGING`. No TLS was built. The C sanitizer exclusion is not
equivalent to Zig's safety instrumentation and was not changed for this test.

## Reservation, cleanup and runner review

Both execution hosts used atomic `/tmp/zig-http-measurement.lock` reservations
and checked pre-existing measurement processes. Mac's benchmark reservation
token was `bd431751-cdb6-485a-bf9e-05ee6cdb8edd`; its runner released it after
the completed run. Linux retained native-verification reservation
`9f0fb179-d099-4a1d-a3f0-dd638c4c16c6` through benchmark cleanup and released it
at `2026-09-06T13:05:23.083053+00:00`.

Review found a failure-path limitation in the executed runner: it waited for
process leaders before killing remaining group members, and set `complete`
before final cleanup. That flag alone does not prove clean process groups.
Independent read-only audits checked every recorded original server PGID with
`killpg(pgid, 0)` and inspected the process table: all 14 server groups per host
were absent, with no matching fixture/client/build processes or owned lock.
The [Mac cleanup audit](2026-09-06-basic-zap/macos/cleanup-verified.json),
[Linux cleanup audit](2026-09-06-basic-zap/linux/cleanup-verified.json) and
[Linux lock lifecycle](2026-09-06-basic-zap/linux/lock-lifecycle.json)
preserve that evidence independently of the runner's completion flag.

The executed fixture archive and receipts remain unchanged. The separately named
[reproducer revision](2026-09-06-basic-zap/reproducer/README.md) hardens cleanup
and completion reporting. Its [ten synthetic macOS tests](2026-09-06-basic-zap/reproducer/validation.json)
passed under a 30-second watchdog; the initial EPERM failure is preserved and
the revision treats uncertain group existence conservatively. This validation
did not build Zig or run HTTP/performance workloads, and does not establish a
Linux test result for the revised runner. No benchmark remains running.
Windows work is deferred until the other session's engine support lands on main.
