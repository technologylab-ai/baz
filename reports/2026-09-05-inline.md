# First inline execution experiment — 2026-09-05

Removing mandatory application-worker handoff gave a **modest improvement**;
it did not explain or close the large gap to the chosen plaintext leaders.
Within the same new sweep, pipeline 16 median throughput rose from 117,479 to
133,648 responses/s (**13.8%**) with inline execution. Pipeline 1 rose from
108,477 to 124,083 (**14.4%**). Inline uses one I/O thread and zero application
workers while retaining access to the same three allowed server CPUs. It is
not a three-I/O-loop implementation.

The original pre-change result remains in
[the first comparison](2026-09-05-comparison.md); it is not silently replaced
by these different source/environment-time samples.

## Execution and ownership

The experiment adds `Execution.inline_event_loop` and `--execution inline`.
It invokes the same application handler and writer with exclusive borrows,
without worker pipes, thread resources or dispatch/wakeup. A result is consumed
by the I/O loop; empty flush/next-buffered-request continuations use bounded
loop turns with a nonblocking poll when local work remains. No callback or
pipeline continuation recurses on the stack.

The caller promises bounded, nonblocking callbacks. Inline code cannot sleep,
block on I/O or wait for a worker without stalling the I/O owner; deadlines
cannot preempt a violating callback. The deliberately blocking demo /stall
returns 501 inline. This is not per-request offload, arbitrary application
isolation or multicore I/O sharding. Worker mode remains available and its
existing hostile wire/ownership suite still passes.

Inline cases cover zero-worker configuration, plaintext/pipeline 16, borrowed
exact-limit echo, chunked partial flush/resume, 128 transport-free HEAD/echo
continuations, malformed/oversize refusal and recovery, admission/deadlines,
and shutdown with incomplete receive plus a genuinely partial borrowed send.
These establish correctness for the named nonblocking demo; they do not prove
preemption. Native receipts are retained in the adjacent directory.

## Next architectural work

The user rejected this level of throughput and asked for performance in the
architecture. Headers were already buffered in memory, but the transport sent
the header and body sequentially, waiting for each completion. That still
serializes 32 sends for 16 ordinary pipelined responses. SQEs may batch across
connections, so this is not a claim of 32 distinct submission syscalls.

Bounded gather-send, buffering several complete responses before flushing,
deferred input compaction, constant-time operation addressing and multiple
I/O owners are distinct next changes. Do not infer that removing assertions,
copying less, or merely selecting io_uring will supply those properties.
